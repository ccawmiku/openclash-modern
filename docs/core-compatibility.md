# Mihomo 内核兼容与升级设计

日期：2026-10-03。状态：开发约束，尚未实现或验证。接口边界已按 OpenClash + MetaCubeXD 复用方向更新，详见 [复用方案](reuse-strategy.md)。

## 1. 目标与边界

普通内核升级尽量只需更换二进制并通过兼容检查。上游新增功能可由适配层逐步开放；发生破坏性变化时，将修改集中在适配层，尽量保持 LuCI、Dashboard 和用户配置不变。

不能承诺兼容所有未来版本。未知版本可以进入验证流程，但不能仅因版本号更大或配置校验通过就宣布兼容。

首个待验证基线为 Mihomo v1.19.32。路由器当前运行的 alpha 版本仅作为迁移输入，不作为长期兼容标准。本设计不意味着立即更新生产内核。

## 2. 四层边界

```text
LuCI 入口 / MetaCubeXD 前端
        ├─ 路由器扩展 → 自有管理 API → OpenClash 后端门面 / 内核适配
        └─ 节点与策略组 → 认证网关 → 保持 Mihomo API 语义
                                             ↓
                                   官方 Mihomo 独立进程
```

- 通过官方进程、CLI 和控制 API 集成；首版不嵌入 Mihomo 内部 Go 包，不维护私人内核分支。OpenClash 和 MetaCubeXD 可维护定制分支，变更尽量集中在扩展接口与明确模块边界。
- 自有路由器扩展中的版本判断与统计字段转换集中在适配层；MetaCubeXD 原有功能遵循其上游 API 客户端，避免复制一套全面转换逻辑。
- 网络接管与防火墙管理有独立模块，显式约定路由表、mark、规则所有权及清理方式。内核自动路由不能与管理服务同时争抢同一组规则。
- 第一版只实现 Mihomo 适配器，保留适配边界即可，不提前开发多个内核。

## 3. 自有配置模型

- 持久化用户意图：节点、策略组、规则来源、DNS 出口、安全模式、监控与优选设置。
- 配置带有自身的 schemaVersion，与 Mihomo 版本分开管理。
- 迁移具有明确输入、输出版本；写入前保留可恢复副本。迁移失败不得覆盖旧配置。
- 不把 Mihomo 的整套 YAML 直接变成用户配置数据库；导入时转换支持项，并报告未转换字段。
- 生成临时 YAML，验证成功后原子发布，避免 sed 或正则反复改写运行文件。
- 显式设置影响路由、DNS、监听地址和协议栈的关键参数，降低上游默认值变化的影响。
- YAML 校验成功不代表字段实际生效；某些未知项可能被忽略，关键行为必须另外验证。
- 高级扩展保留命名空间、字段归属和合并顺序。发生冲突必须报错；扩展不得覆盖受管理的认证、监听范围或严格出口保护约束。

## 4. 自有管理 API 与统计模型

- 路由器管理 API 自行版本化。MetaCubeXD 已有的 /connections、/traffic、/proxies 等调用经认证网关保持 Mihomo API 语义；不全面复制、重命名或改写上游 API。
- 网关对读请求和普通节点选择尽量保持兼容；配置写入、内核升级及影响严格出口的操作必须通过统一管理流程或明确限制，避免绕过配置所有权与安全约束。控制 API 不作为任意 root 命令执行入口。
- 适配层转换连接、策略组、速率、计数器和错误，明确单位、采样时间、内核运行周期及统计来源。
- 容忍响应中新增的未知字段；缺失的可选字段表示 unavailable，不能当作零或正常状态。
- 缺失关键字段时禁用受影响操作并解释原因，不能伪造成功。
- 将内核连接 ID 与运行周期组合，处理内核重启、计数器归零和连接 ID 重用。
- 设备总量、内核流量与 WAN 字节独立记账，不直接相加；对采样遗漏和代理开销说明统计范围。
- 不依赖日志字符串实现核心状态判断；诊断日志允许按版本扩展。
- 目标设计中内核控制接口限于本机；MetaCubeXD 与 LuCI 通过经过认证和授权的网关访问。HTTP 与 WebSocket 均需验证，使用同源路径和明确授权。令牌不写入日志或统计记录。过渡方案如保留 LAN 9090，必须限制接口、来源和访问权限，不能称作最终认证方案。

## 5. 能力识别与安全降级

能力信息由版本规则、非破坏性 API 探测及隔离验证共同形成。Mihomo 的 /version 仅提供版本信息，不能假定上游存在统一能力查询接口。

- 保存版本、二进制摘要、已验证能力和验证结果。
- 从最少必要的 API 与配置字段起步；新功能通过能力开关启用。
- 对未知版本报告“未验证”，允许继续做验证，不自动判为全部支持或全部不支持。
- API 探测不可修改生产策略组、清空连接或重启服务。
- 配置字段的接受情况、实际应用情况与真实网络行为分开检查。
- 可选图表缺少数据时可以降级；DNS 出口、IPv6 接管和故障阻断等安全要求缺失时拒绝启用候选版本。
- 支持范围按具体已验证版本和能力记录，不声称整个未来版本区间已通过测试。

## 6. 升级事务

内核更新与管理插件更新独立发布。默认采用经过验证的稳定版本，不在后台无条件替换最新版本。

1. 获取候选版本；核对下载来源、架构、CPU 指令要求和发行方摘要。摘要校验不等同于签名验证；上游提供签名时另行校验。
2. 在备用目录保存候选二进制、为其生成的配置与所需规则资产，保留当前运行组合。
3. 使用候选二进制做 CLI 配置校验；命令选项由适配器确认。
4. 在独立 network namespace 或测试设备验证启动、API 和关键行为。仅修改端口并不足以隔离自动路由、TUN 与 nftables；不能在生产路由空间直接运行候选自动接管。
5. 获取升级锁，记录持久化事务状态。保持严格模式防火墙保护，执行受控切换与生产健康检查。
6. 验证失败恢复旧二进制、旧配置、规则资产及相匹配的可变状态；不只恢复一个可执行文件。
7. 验证通过后标记为已验证组合，保留至少上一套可用组合。

升级过程中也要覆盖存储空间不足、断电、进程退出和服务重启；下次启动按事务状态恢复。候选版本可能改写缓存格式，所以可变状态应分版本隔离或在迁移前备份。

严格模式保护由防火墙模块维护，不能随内核停止而删除。恢复旧内核时也不能通过临时开放公网转发维持可用性。

## 7. 兼容验证

维护少量有意义的测试，而非每个版本复制一套业务代码：

- 配置样例：VLESS Reality、VLESS WS、TUIC、DNS 出口、IPv6 与策略组；以真实候选二进制验证。
- API 合约：旧响应、新增字段、可选字段缺失、关键字段缺失、错误响应及重连。
- 统计行为：重启归零、短连接遗漏、节点切换与不同字节口径。
- 升级行为：配置拒绝、启动失败、健康检查失败、资产不兼容、断电恢复和回滚。
- 隔离网络验证：TCP/UDP、IPv4/IPv6、DNS 引导、WAN 抓包、内核退出和 firewall 重载。
- 性能比较：同硬件、节点、规则与负载下比较吞吐、延迟、CPU、内存和采样成本。

发布前覆盖当前已验证版本、上一套可回滚版本与候选版本。配置解析和 API 探测不能替代 WAN 抓包；包捕获也不能证明所有未来应用均无泄漏。

## 8. 对前端的稳定承诺

普通内核升级不要求前端重新部署。新功能通过后端能力信息展示；受支持操作的输入输出保持稳定。

上游删改字段时优先在适配器中转换或实施有明确边界的兼容处理；如果关键语义无法保持，则解释不兼容原因并停止升级。性能敏感路径避免额外全量 JSON 复制、无界日志与高频磁盘写入，采用有界采样与批量存储。
